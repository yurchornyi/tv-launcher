# Агентам і розробникам

Увесь AI цього проєкту йде через Sentra, центр AI власника. Перед будь-якою зміною AI-викликів, промптів, лімітів, кешу, сповіщень чи секретів прочитай [SENTRA.md](SENTRA.md): там сказано, що Sentra вже робить і чого не можна дублювати.

## Розмір змін: задача цілком, один push

12.11, рішення власника, для всіх проєктів і агентів (Claude Code, Codex та інших): не працювати кусками «трохи зробив — запушив». За 05–12.11 так вийшло 288 PR у KURO, 76 у KURObots, 64 у Sentra; більшість злито менш ніж за 30 хв одна після одної, багато — на 1–30 рядків. Кожен push — це прохід CI на ПК, а кожне злиття — ще й деплой.

- **Одна задача — одна гілка, один PR, один push**, коли задача готова цілком: код, тести, документація й дрібні правки поруч. Не ділити задачу на окремі PR («правила», «сервіс», «вікно»).
- **Не пушити після кожного кроку чи кожної відповіді власнику.** До готовності — локальні коміти, скільки треба.
- **Доводь задачу до кінця сам**, перш ніж пушити: сусідні місця, які зачіпає та сама зміна, і те, про що власник інакше попросив би наступним повідомленням (вузький екран, тексти, тести, документація).
- **Уточнення власника до тієї самої задачі** — у ту саму гілку й той самий PR, поки його не злито. Після злиття уточнення однієї теми збирай в один наступний PR, а не по PR на кожне.
- **Перед новим PR** — `gh pr list`: є твій відкритий PR на ту саму тему — додай туди.
- **Червона перевірка** — усі виправлення за логом одним push.
- **Окремий малий PR** (до ~30 рядків) — лише коли без нього зламано production чи `main` або власник прямо просить запушити зараз.

## Автозлиття

PR зливається в `main` сам, щойно всі його перевірки зелені (`.github/workflows/merge-when-green.yml`, рішення власника 31.10, для всіх сесій). PR, який ще не готовий або має лишитись відкритим, відкривай як чернетку (`gh pr create --draft`). Автозлиття не чіпає PR від ботів і PR із міграцією. На Mac перевірки не запускай: ні тестів, ні lint, ні typecheck, ні збірки (12.11, рішення власника, для всіх проєктів і сесій: на Mac лише пишеться код і збирається ядро браузера). Зробив push — перевіряє CI; червону перевірку виправляй за її логом. Не проси власника натискати «злити». Змінна репозиторію `AUTO_MERGE=false` вимикає автозлиття.

## CI: де йдуть перевірки

Однаково в усіх проєктах власника (10.11, рішення власника, для всіх сесій):

1. **GitHub-hosted** спершу, поки є безкоштовні хвилини місяця. Job `GitHub-hosted availability` пробує `ubuntu-latest` (лише на `pull_request`); коли хвилин нема, він червоний: це очікувано, автозлиття його не рахує, не перезапускати й не розслідувати. Тоді job-и самі йдуть на ПК.
2. **ПК власника** (Windows, 4 ядра, 16 ГБ, завжди ввімкнений): перевірками керує **диспетчер** (12.11, рішення власника: одна система). Він живе в `C:\Fleet` (завдання «Fleet Dispatcher», джерело — `agent/fleet/` у репозиторії `sentra`, правила — `docs/FLEET_UA.md` там само): дивиться чергу GitHub усіх приватних репозиторіїв і під кожну задачу запускає одноразовий runner у вільний слот — 2 перевірки разом удень, 3 у «Максимумі», 1 у «Тихому»; задачі на секунди (автозлиття, рішення про деплой) проходять завжди. Мітки в workflow лишаються як були (`<проєкт>-ci`, `<проєкт>-pc`, `<проєкт>-quick`): диспетчер дає runner-у мітки самої задачі. **Старі runner-и (`ghr*`, завдання «… GitHub Runner») вимкнені й мають лишатися вимкненими: не вмикай їх, навіть коли задача чекає** — разом із диспетчером вони перевантажують ПК (12.11: 100 % процесора) і забирають задачі раніше, ніж їх можна поділити. Задача чекає — дивись `C:\Fleet\status.json` (там причина) і `C:\Fleet\logs\dispatcher.log`. Режим ПК (тиша, тихий, максимум) — це запис із терміном, який ставить власник у «Пульті» на Mac або `node C:\Fleet\app\dispatcher.mjs mode …`; вимикати завдання Windows заради тиші заборонено (12.11: так черга простояла 12 годин). Перевірку, що впала не з вини коду, диспетчер перезапускає сам (`ci-doctor.mjs`): вручну перезапускати не треба.
3. **Приставка власника** (ROG Xbox Ally X) — ігрова; перевірки на ній можливі, але за замовчуванням вона вимкнена, і вмикає її лише власник кнопкою в «Пульті» (12.11). Тоді диспетчер ПК сам запускає на ній перевірки по SSH; токена GitHub і зареєстрованих runner-ів на ній немає. Недоступна в грі, на батареї, поза домашньою мережею і коли вільно менше 25 ГБ. Усе там лежить у `C:\Fleet` плюс одне завдання без тригера «Fleet Awake»; ядро браузера на ній не збирається. Нічого іншого на приставку не ставити.
4. **Mac у CI не задіюється.** Єдиний виняток — `.dmg` для KURO Desktop release.

Workflow: після probe `runs-on` — `ubuntu-latest`, інакше `["self-hosted", vars.CI_RUNNER || <мітка>]`; checkout з історією (`fetch-depth: 0`) — з `filter: blob:none`; на self-hosted без завантаження кешу GitHub (залежності лишаються на диску runner-а, `runner.tool_cache`); перевіряти лише те, що зачіпає зміна; тест не залежить від ОС (Linux на GitHub, Windows на ПК) і години доби. Публічний репозиторій — лише GitHub-hosted (хвилини безлімітні); self-hosted runner до нього не підключати: чужий PR запустив би код на ПК.

У цьому репозиторії (публічний) усе йде на `ubuntu-latest`: `CI`, `Release`, автозлиття.
